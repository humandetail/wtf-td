# Integration contract

All original assets are read-only. Application files are native ES modules. No production dependencies.

## Seven distinct game modes (current integration)

Current specification: docs/distinct-modes-redesign.md. createGame routes all seven mode values: loop (default), defense, escort, maze, gem, hero and legion. The final three delegate to createGemGame, createHeroGame and createLegionGame in independent session modules. The old harvest/storm variants were superseded after user feedback; they are no longer offered. UI owns seven separate in-memory sessions and returns ended sessions to their reports; only explicit restart clears a session.

Loop keeps its original v5 random road network, 80-enemy cap and 20-wave clear. Defense keeps its four finite lanes, 20 core health, independent per-enemy lane, 20-wave clear and 40+5*wave clear supply/12s preparation. New modes do not change these rules.

Escort is a moving-target delivery mission, not static core defense. escort-geometry.js owns exact S route (length2480), checkpoints800/1600, width48 and full-footprint exclusions. state.convoy has x/y/angle/progress/length/moving/checkpointIndex; coreHealth/maxCoreHealth start100. Enemies store routeProgress, chase toward the vehicle from front/back wave-fixed ambush points, face travel direction and stay to deal2.5/s (Boss7/s) melee damage instead of disappearing. At each checkpoint auto-stop and supply100 once; delivery wins, zero health loses first, no endless. Public toggleConvoy(), repairConvoy() (stopped,60gold,+6health), canRelocate(id,x,y)/relocate(id,x,y) (25gold,retainID/level/spent,readyAt=elapsed+3). During downtime no combat, aura or income. Relocation fee is not resale value. All positions remain continuous and unsnapped.

Maze is player-controlled routing across an open arena. maze-geometry.js reverse BFS/flow snapshot with20px internal navigation (not placement slots), full footprints plus10px enemy clearance, continuous orthogonal motion. New layout validates entry and all live enemy routes, rejects covering enemies/next targets or last-path sealing. state.walls contains negative-ID WALL objects, state.mazeRoute/mazeLength are public guidance; nav stays private. canBuildType/canBuild/build accept WALL only in maze:20gold,60x60,limit24,does not count tower capacity. sell(negativeId) refunds15; no wall upgrade. Ordinary tower placement also changes routing. Each successful build/sale rebuilds flow; in-flight enemies reattach continuously.12 waves, Boss every4, preparation10s after clear, supply40+5*wave,20 exit health; victory then endless retain wall layout/health/research.

Scenes are separate: loop=v5, defense=core-defense, escort=escort, maze=maze. New grounds contain no baked roads; runtime ground-guidance follows exact escort geometry or actual maze flow. Original P01 supply crate is the vehicle and P02 generator with native energy field is the wall. Initial images:24 unit masters+6 effects+7 scenes+3 props (P01/P02/P04)+3 atlases=43. Both original base maps and all original assets stay unchanged.

New state common fields are convoy(null outside escort),walls([] outside maze),mazeRoute,mazeLength,ambushPoints; original tech/research/commands/events stay shared. Added events checkpoint,convoy-toggle,convoy-repair,relocate. main mission controls share the existing non-resizing overlay; selected walls use hitTest and sell; relocating placement carries towerId/relocating with the authoritative canRelocate status. state.mode selects background/mask; no main-map layout change when opening build/research/mission panels.

## Center spawning and research integration (2026-10-31)

User authorized implementation after Q1–Q12. ENTRY becomes (640,400); createRoadPosition(random) chooses up/right/down/left in equal quarter intervals of [0,1), and spawn uses the same session RNG as subsequent junction choices.

State adds tech `{deployment:0,reinforcement:0}` and research `null | {kind,level,cost,duration,remaining}`. New public commands/checks: canBuildType(code), canUpgrade(towerId), canResearch(kind), startResearch(kind), cancelResearch(); each returns `{ok,message}` and mutations use the corresponding checks. Kinds are deployment and reinforcement. Existing canBuild also checks geometry. All gates use completed tech only. In the original four modes, research can be operated during a paused playable session, with progress frozen like other simulation time; finished or failed sessions reject mutations.

research.js exports TECHNOLOGIES (each kind has name and levels), deploymentStats(level) returning `{capacity,unlockedCodes}`, towerUnlockLevel(code). Each level has cost and duration; deployment levels additionally have capacity and unlocks (new codes at that level), reinforcement levels have maxTowerLevel. Levels include index 0 with cost/duration 0. Full values and types follow the spec. Global research is single-task, charged once, cancel-refunded once, and preserved frozen at victory for endless continuation. Events research-start/research-complete/research-cancel carry message and research kind; no renderer-private access is needed.

New DOM IDs: research-panel, deployment-level, reinforcement-level, deployment-details, reinforcement-details, deployment-research-button, reinforcement-research-button, research-progress, research-status, cancel-research-button, tower-capacity.

## Three additional session boundaries

The constructors are exported by gem-session.js, hero-session.js and legion-session.js. Each owns its state, clocks and command validation; all expose start(), restart(), tick(seconds), togglePause(), setSpeed(1|2|3), drainEvents(), canResearch(kind), startResearch(kind) and cancelResearch(). The UI reads each session's catalog, technologies and statsFor(unit) when provided; Hero reuses catalog.js/research.js and effectiveTowerStats. New modes keep convoy=null and walls=[] for the common render boundary. Pause, menu and terminal phases stop simulation on all battlefields.

Gem exposes draw(), reroll(), keep(candidateIndex,{x,y}|{inventory:true}), merge(primaryId,materialId), forge(recipeCode,primaryId,materialIds), store(id), deployInventory(id,x,y), sell(id), startCombat() and launchWave(). state.draft holds the five candidates and refresh count; state.inventory is the two-slot reserve, and state.scraps/pity/drawOrder expose the scrap and seeded pity systems. The selected gem is a real unit; fusion consumes actual material IDs. canBuildType/canBuild/build and canUpgrade/upgrade reject ordinary shop construction and cash upgrades. recipes and capacity() are public. Twenty cleared waves win; no endless continuation.

Hero exposes setMoveVector(dx,dy) (alias moveHero), moveHeroTo(x,y), targetEnemy(id), castSkill('Q'|'E'|'R',x,y), chooseCampReward(choice), upgradeEquipment(), launchWave(), and ordinary build/upgrade/sell checks and commands. state.hero holds actual position, health, mana, level, experience, equipment, action, cooldowns and respawn state; state.camps/pendingCampReward/campRewards and telegraphs are public. Movement resolves collisions, hunters use aggro/leash, caster and boss telegraphs can be interrupted or avoided, and the goddess owns the persistent core health. The 15-wave campaign has no endless continuation.

Legion exposes startCombat(), buyWorker(), queueMercenary(code), cancelMercenary(orderId), upgradeKing(), canBuildType/code checks, build(x,y,code), canUpgrade(id), upgrade(id), sell(id), publicIntel(side), scout(side), and commandsFor('player'|'ai') for equal legal side commands. It also exposes reset(), setPaused(value), returnToMenu(). state.sides.player and state.sides.ai each own king, fighters, invaders, pendingInvaders, gold, mythium, workers, income, tech, research, orders, committedOrders, ledger and round report. Common state.towers/enemies/gold/coreHealth/tech/research are live player aliases and continue pointing at fresh state after restart. The renderer projects the selected side's fighters/invaders/king into one full-size battlefield using viewSide; changing the view never redirects player build commands to AI. The UI maintains both kings in legion-kings and switches scouting via scout-button. AI plans through the same commands when entering planning, before the player edits the next round; locking does not rebuild its visible roster or inspect pending opponent orders. Uncommitted orders and hidden funds are omitted from publicIntel.

Legion king death determines victory/defeat, and damage from both battlefields is collected before resolution so simultaneous king death yields draw. Combat units retain health, move, collide and attack; circle sweeps constrain every move before committing, including boundary sliding. Nonoverlapping staging positions sit north of deployment, and larger waves retain pendingInvaders until a real spawn vacancy exists; surviving invaders fight the king, with leaks counted at actual king engagement range. Round reports, ledgers and side-tagged damage/death events are public. All fighters restore their saved formation and health at settlement; king damage persists. Each round grants income gold and 12+2*workers mythium once. Mercenary orders reserve mythium, refund on cancellation, add permanent income only when committed, and enter the opposing battlefield. There is no finite-wave automatic victory.

Gem and Legion use manual planning/combat phases: editing and starting/cancelling research require unpaused planning, while research progress advances only during combat. Preparation grants no elapsed simulation time or passive resources. Hero research commands require an unpaused playing session and research progresses during active simulation, including between waves. The shared createResearchControls(state,emit,definitions,allowed) helper owns the single charged/refunded research transaction; each session owns when to call advanceResearch(dt).

The 17 new static DOM IDs are mode-gem-button, mode-hero-button, mode-legion-button, hero-hud, legion-hud, legion-kings, scout-button, gem-selection-actions, special-mission, hero-status, hero-skills, hero-q-button, hero-q-state, hero-e-button, hero-e-state, hero-r-button and hero-r-state. Mode-specific mission controls are populated inside special-mission and retain the existing overlay layout.

Three dedicated opaque scenes live at assets/maps/{gem,hero,legion}/scene.png and are byte-identical to their retained source/scene-imagegen-original.png. The separate Hero revision-2 source is preserved but is not the adopted scene. Transparent generated atlases are assets/modes/hero/atlas.png (8 directions × 5 action rows), gem/atlas.png (4 × 3: six gems, five recipes, fusion effect), and shared/objectives.png (four uneven crops: goddess, king, two camps; OBJECTIVE_FRAMES in special-render.js). Atlas source originals and prompts are retained; hero columns/gem cell clipping supports fractional pixel boundaries, hero rows use HERO_ROW_BOUNDS, and objective crops preserve actual aspect ratios. The adopted Hero scene removes the baked southern dais; the independent goddess sprite owns its exact coordinate. Asset sizes, action rows and ground anchors are documented in assets/modes/README.md. scripts/check.mjs verifies opaque scenes, source equality, image ratios, transparent visible content in every atlas cell, 17 added DOM IDs, syntax, and the unchanged 808-file original baseline. Pixel checks establish file structure and occupancy, not subjective art acceptance.

## Geometry

World is 1280 × 800. The active v5 map follows the supplied reference: outer ring, inner ring, central cross and four connecting spokes. Roads are 48 pixels wide, with planted shoulders. ROAD_PATH and ROAD_SEGMENTS describe the same artwork and collision network. ROAD_NODES splits those roads at all intersections and endpoints. Each enemy starts at central ENTRY (640,400), independently chooses one of four cardinal directions, then chooses uniformly among onward exits on arrival at a junction, excluding the road just travelled. Corners turn automatically. There is no fixed patrol or terminal node; surviving enemies remain on the network. All angles are radians, screen y points down. v1/v2/v3/v4 art and layout snapshots remain preserved.

FOOTPRINT is 90×50 with 8 pixels between buildings. BUILD_BOUNDS contains full footprints; BUILD_CENTER_BOUNDS and BUILD_EXCLUSIONS describe allowed anchor positions after expanding roads and the hub by footprint plus clearance. placementStatus(x,y,towers) is the single geometric check. Positions are continuous and unsnapped; there are no SLOTS or preset construction points.

## Public game session

For the original four modes, `createGame(options = {})` from engine.js returns an object with `state`, `start()`, `restart()`, `tick(seconds)`, `canBuildType(code)`, `canBuild(x,y,code)`, `build(x,y,code)`, `canUpgrade(towerId)`, `upgrade(towerId)`, `canResearch(kind)`, `startResearch(kind)`, `cancelResearch()`, `sell(towerId)`, `togglePause()`, `setSpeed(number)`, `continueEndless()`, `drainEvents()`.

Optional public `launchWave()` starts the next wave early when no spawn queue remains; it returns `{ok,message}` without extra gold. The current UI uses automatic scheduling. Session options for repeatable checks are startingGold (400), limit (80), waveInterval (26), spawnInterval (.65), initialDelay (18), waveCount (20), waveSize (wave=>count), enemyHealthScale, enemySpeedScale and rewardScale (each 1), and random (Math.random; must return a value in [0,1)).

State has phase ('menu' | 'playing' | 'victory' | 'defeat'), paused, speed, gold, wave, nextWaveIn, elapsed, kills, endless, limit, towers, enemies, tech and research. Preview and mutation share canBuild checks for geometry, funds, phase, catalogue, completed deployment unlocks and capacity. Successful build returns `{ok,message,towerId}`; failures and upgrade/sell return `{ok,message}`. Failure never charges or allocates an ID. Ticks apply chosen speed and stop when paused or not playing. Restart resets the session and independent tower/enemy ID counters; continueEndless retains towers and currency.

Tower fields: id, code (T01–T12), level, spent, x, y, angle. IDs identify buildings independently from location; selling and rebuilding at the same coordinates creates a new ID. Enemy fields: id, code (X01–X12), hp, maxHp, x, y, angle, progress (total travelled distance, retained for target priority), roadFrom/roadTo (current graph edge), boss, slowUntil (simulation seconds, optional). Movement consumes the full distance across as many junctions as necessary, preserving position continuity and updating facing on turns. Shot effects go through events rather than renderer internals.

Events drained by the UI: `{type, x?, y?, tx?, ty?, code?, amount?, color?, message?}`. Types include shot, hit, kill, build, upgrade, sell, wave, victory, defeat, research-start, research-complete and research-cancel. Damage is resolved by the session. UI and audio only display outcomes.

## Scene artwork

v5 loads a single painted scene.png containing the terrain, all lanes and the central seal; it never overlays an independently styled road image. Initial artwork loading totals 43 images: 24 unit masters + 6 effects + 7 scenes + 3 props (P01/P02/P04) + 3 atlases. The scene and retained ImageGen original are byte-identical. Rendering applies one subtle scene-wide stone tint and separate actor shadows; original images remain untouched.

Road motion and placement remain authoritative in geometry.js. The painted scene is checked with actual paving-color samples away from ornaments, plus the full route inspection overlay and independent visual review. Color heuristics are approximate and do not substitute for inspecting junctions or real-browser acceptance.

## Catalogue

`catalog.js` exports TOWERS and ENEMIES arrays with code, name, assetId, description, color, and stats. Tower definitions contain price, damage, interval (seconds), range (world pixels), kind. `towerStats(tower)` returns level-adjusted damage/interval/range/upgradeCost/sellValue and any UI relevant stats. MAX_LEVEL is exported. All source imagery is looked up through the original manifest by code.

`towerStats` describes base level-adjusted stats; `effectiveTowerStats(tower,towers)` additionally applies live radar and overclock auras, and is shared by combat, range rendering and displayed attributes. Supply income emits an `income` event with amount, x, y and color.

## Battlefield layout

The default battlefield uses the viewport after a compact HUD. The bottom construction dock is an absolutely positioned overlay inside battle-stage, opens on demand and closes after picking a tower. Opening/closing it never changes stage or canvas bounds; the game grid always has HUD and stage rows, and the toggle has fixed width to prevent header reflow. Research and selected-unit details share a non-modal right drawer, closed by button or Escape with focus restoration. Opening research closes the construction dock. The focus/build control stays available in the HUD; restart restores the default map-first state.

A ResizeObserver fits the canvas to the actual stage while preserving 1280:800. Its CSS box matches the painted map, so existing pointer mapping uses the true canvas bounding rectangle; there is no object-fit letterboxing inside the input target. Narrow/short viewports keep bounded scroll areas for controls. Drawn world geometry, research and session rules are unchanged.

## Verification boundary

One public session boundary verifies player commands and visible outcomes via a runnable session check, plus independent read-only asset hashing. Real-browser full playthrough, audible verification and subjective map/balance acceptance are reserved for the user after implementation. Do not run a full real-browser suite now. Never mark human acceptance complete on behalf of the user.

Hero HUD is an absolute bottom overlay with hero-status and three persistent Q/E/R buttons. Skill buttons show live unlock, mana, cooldown, pause and respawn state; arming restores canvas focus. In Hero only, the build dock opens above the skill HUD without changing stage/canvas bounds. Right-click first cancels an armed action and only moves/targets when unarmed.

## Mobile web controls (2026-11-02)

mobile.css preserves the bronze/jade palette and supplies SVG mask command icons with text names, including paused/muted states. Small screens/coarse pointers automatically add touch-layout; ?mobile=1 forces the same responsive web version. The bottom command bar and bottom sheets are overlays and never resize canvas bounds. Portrait and landscape retain full-world fit, optional 1.5/2x zoom and camera dragging; pointer coordinates use the transformed canvas bounding rectangle. Safe-area insets and 44px primary targets are supported.

createTouchControls(canvas,callbacks) previews touch actions, requires separate confirmation before issuing the original game command, suppresses synthetic clicks, cancels multitouch/drag purchases, and supplies a hero joystick. reset/clear/stop integrate with menus, dialogs, pause and mode changes. Hero taps without an armed action select towers, target enemies or move to open ground. Desktop click/right-click/keyboard continue on their original boundary. No native app or persistent save was added; refreshing still resets sessions as before.

The static server defaults to loopback. Explicit HOST=0.0.0.0 opts into LAN hosting, e.g. PORT=4174, exposing only the existing game/outputs allowlist. Real device/browser layout, gestures and audio acceptance remain assigned to the user.
